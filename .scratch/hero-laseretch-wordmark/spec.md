# Hero laser-etch wordmark

Status: ready-for-agent

## Problem Statement

The homepage already renders the approved 81-column by 10-row `OMARCHY` ASCII wordmark through `_includes/wordmark.html`, but `src/js/wordmark.js` applies a continuous three-color sweep. That effect is an approximation. It neither matches the one-shot laser-etch animation on [omarchy.org](https://omarchy.org/) nor settles into a finished mark.

The reference homepage progressively enhances the same ASCII text with Web Text Effects. A local Canvas renders the `laseretch` effect from a pinned WebAssembly module, plays once, and holds the final frame. The `<pre>` remains the layout owner and static fallback. Reduced-motion, no-JavaScript, print, and load-failure paths show the ordinary Green wordmark instead.

This repo needs that exact animation behavior without adding a remote runtime dependency, changing the homepage composition, or weakening the existing production and accessibility gates.

## Solution

Replace the current looping wordmark renderer with the production `laseretch` integration used by omarchy.org. Vendor the exact Web Text Effects runtime and WebAssembly artifacts locally, load them only on a page containing `[data-wordmark]`, and use the existing ASCII `<pre>` as the effect input, sizing reference, and fallback.

Play `laseretch` once after the primary JetBrains Mono face is ready or a one-second font wait expires. Render into the existing decorative Canvas at the `<pre>`'s dimensions. When playback finishes, keep the final Canvas frame visible; do not loop or replay it. If enhancement is unavailable or fails, reveal the static Green `<pre>` no later than two seconds after first paint.

Make a clean cutover. Delete the current `COLORS` sweep, continuous `requestAnimationFrame` loop, and `IntersectionObserver` lifecycle rather than retaining them as an alternate effect.

## User Stories

1. As a homepage visitor, I want the `OMARCHY` mark laser-etched into view once, so that the first screen carries the same signature motion as omarchy.org.
2. As a visitor who remains on the page, I want the completed wordmark to stay still, so that the hero does not become a permanent source of motion.
3. As a returning visitor who reloads the homepage, I want one fresh playback for that document load, so that playback has a simple and predictable lifecycle.
4. As a visitor on a phone, tablet, or desktop, I want the animated mark to occupy the static wordmark's exact box, so that enhancement causes no layout shift or overflow.
5. As a visitor who prefers reduced motion, I want the static Green wordmark immediately, with no Canvas playback or effect downloads.
6. As a visitor without JavaScript, I want the static Green wordmark immediately, so that the brand and hero layout remain complete.
7. As a visitor whose browser cannot load or execute WebAssembly or Canvas, I want the static Green wordmark within two seconds, not an empty gap.
8. As a print user, I want the static Green wordmark and no Canvas output.
9. As a screen-reader user, I want one useful `Omarchy` name while the generated Canvas remains ignored.
10. As a maintainer, I want the effect runtime pinned and locally served, so that the homepage does not depend on mutable third-party URLs.

## Reference Contract

The implementation target is the omarchy.org production behavior inspected on 2026-08-31. Preserve these constants and lifecycle decisions:

| Contract | Required value |
|---|---|
| Effect | `laseretch` |
| ASCII geometry | 81 columns by 10 rows |
| Terminal cell aspect | 2:1 height to width |
| Font wait | `document.fonts.ready`, capped at 1,000 ms |
| Logical effect frame rate | 240 |
| Playback count | Once per homepage document load |
| Completion | Empty `onFinished()` callback; retain final frame |
| Canvas compositing | `mix-blend-mode: screen` |
| Fallback deadline | Two seconds after first paint |
| Motion opt-out | `prefers-reduced-motion: reduce` skips runtime loading and Canvas creation |

The effect chooses its own session seed. Do not introduce a fixed seed or reproduce the output with hand-authored colors. The final reference frame contains the blue, cyan, white, and purple palette generated by the WebAssembly effect; it is not the current three-color sweep and it is not recolored Green by application code.

At a 1440 by 900 CSS-pixel viewport with device pixel ratio 1, the reference `<pre>` measured approximately 722.5 by 175 pixels. Its native terminal grid was 648 by 160 pixels: 81 columns of 8-pixel cells and 10 rows of 16-pixel cells. CSS scaled that native Canvas to the `<pre>` box. Other viewports derive their grid from the measured `<pre>` rather than hard-coding those desktop dimensions.

## Implementation Decisions

### Progressive enhancement and markup

- Keep `_includes/wordmark.html` as the canonical owner of the exact ASCII art. Do not duplicate the art in JavaScript, YAML, an image, or the WebAssembly bundle.
- Keep one existing `<canvas data-wordmark-canvas aria-hidden="true">`. Do not create a second Canvas or replace the semantic fallback with a custom element.
- Keep one accessible `Omarchy` name on the wordmark container. The fallback must not create a duplicate announcement, and the Canvas remains decorative.
- Add locally resolved runtime and WASM URLs to the wordmark as `data-*` values rendered through Liquid's `relative_url`. JavaScript must not assume the site is deployed at `/`.
- Add a tiny pre-paint capability class from the document head. Static fallback is the default; CSS hides it only when that class is present and motion is allowed. This removes dependence on `<noscript>` as the only recovery path.

### Runtime integration

- Replace `src/js/wordmark.js` with the one-shot loader modeled on the pinned production `logo.js`.
- Do not bundle the 204,609-byte WTE payload into `assets/js/site.js`. Fetch and dynamically import the local runtime only after finding a valid wordmark and confirming motion is allowed. The existing 61,440-byte gzip budget remains an initial-JavaScript budget.
- Load the WebAssembly bytes once and pass the `ArrayBuffer` to the WTE binding. Do not use a remote URL or fetch the binary more than once.
- Preserve the production compatibility adapter: inspect the pinned `wte-canvas.js` module for its `./assets/playback-*.js` import, dynamically import that local module, and identify the playback constructor by its `restart()` and `stop()` prototype methods. The public `<wte-canvas>` element is not used because it loops.
- Construct playback with the existing Canvas, the ASCII fallback text, `effect: "laseretch"`, `frameRate: 240`, and an explicit no-op `onFinished` callback. An omitted callback restarts playback and violates the one-shot contract.
- Let the playback runtime own the device-pixel-ratio backing store. Application code owns only the native terminal-grid CSS dimensions and scale.
- Do not add `IntersectionObserver`. Scrolling away and back, resizing, changing tab visibility, or opening and closing navigation must not restart a completed effect.
- A `ResizeObserver` may update only the Canvas scale. It must not create a new WebAssembly session or replay the effect.

### Sizing and presentation

- Derive the native cell width as the floored minimum of `preWidth / 81` and `preHeight / (10 * 2)`, clamped to at least one pixel.
- Set the native CSS Canvas size to `cellWidth * 81` by `cellWidth * 10 * 2`, then independently scale its X and Y axes to the current fallback bounds with `transform-origin: 0 0`.
- Keep the wordmark container `position: relative`; keep the Canvas absolutely inset over the fallback and clipped to the wordmark box.
- Use `mix-blend-mode: screen`. Do not add an opaque Canvas background, filter, application palette, glow, or extra transition.
- The fallback continues to use `var(--omarchy-green)`, the existing JetBrains Mono face, and the current responsive type sizing.
- Canvas activation must not change the wordmark's intrinsic block size. The hidden `<pre>` remains in layout throughout playback and after completion.

### State and recovery

Use the existing `data-wordmark-enhanced` contract:

- Attribute absent: enhancement has not produced a live Canvas yet. The two-second CSS recovery timer is active.
- `data-wordmark-enhanced="true"`: a Canvas has been attached and playback has started successfully. Cancel the fallback timer, hide the `<pre>` visually, and show the Canvas.
- `data-wordmark-enhanced="false"`: enhancement is unavailable or failed. Stop playback, disconnect observers/listeners owned by it, hide or clear the Canvas, and show the fallback.

Treat all of these as fallback conditions: missing elements, empty ASCII input, reduced motion, print mode at initialization, missing Canvas 2D context, invalid dimensions, failed runtime fetch/import, failed WASM fetch/compile, playback rejection, and WebAssembly runtime errors. Recovery must not leave a rejected promise or uncaught `RuntimeError` in the page.

If JavaScript starts but never reaches either terminal state, CSS must reveal the fallback after two seconds. Once a live Canvas is confirmed, cancel that timer so the fallback cannot appear through the animation.

### Vendored assets and provenance

- Publish the pinned WTE loader, playback runtime, binding glue, and `laseretch.wasm` below `assets/js/wte/` with the reference relative-path relationships intact.
- Add manifest records for all four files, including source URL, inspected date, SHA-256, byte size, rights owner, actual license or first-party permission basis, and `publication_status: cleared`. Public availability is not itself a license; do not invent one.
- Extend the production verifier to require those files and their pinned hashes. An intentional WTE upgrade must update the hashes, provenance, compatibility adapter, and browser evidence together.
- Keep every runtime request same-origin. No new remote script, module, font, frame, or media source is allowed.
- Add no npm dependency. The vendored browser runtime is the pinned dependency.

## Testing Decisions

The highest seam is the production build plus the existing rendered-site Chromium verifier. Test the rendered wordmark and real Canvas behavior, not source strings or private WTE class names.

### Automated checks

1. **Normal motion:** At 390 by 844, 768 by 1024, and 1440 by 900, the wordmark fallback has nonzero dimensions, the Canvas reaches the enhanced state, and the Canvas and fallback bounding boxes agree without horizontal overflow or layout shift.
2. **Actual playback:** Sample the Canvas after enhancement and prove its pixel output changes during playback, then becomes stable after completion. Allow the effect's random seed; do not compare a complete frame hash.
3. **One shot:** After the output stabilizes, scroll the wordmark out of view and back, resize the viewport, and switch document visibility where the harness permits. The stable Canvas frame must not change and no second session may begin.
4. **No JavaScript:** Block the site bundle. The Green fallback is visible immediately and the hero retains its layout. Update the existing no-JavaScript assertion rather than adding a duplicate test.
5. **Reduced motion:** Emulate `prefers-reduced-motion: reduce` before navigation. The Green fallback is visible, the Canvas is not displayed, and no request for `/assets/js/wte/` occurs. Extend the existing reduced-motion assertion.
6. **Load failure:** Block `laseretch.wasm`, then separately block the playback module. Within two seconds the state is static, the Green fallback is visible, the Canvas is hidden, and the page reports no uncaught exception or unhandled rejection.
7. **Print:** Emulate print media. The static fallback is visible and Canvas output is absent.
8. **Production artifacts:** Require the four vendored files, exact SHA-256 hashes, same-origin URLs, and valid manifest clearance records. Keep `assets/js/site.js` within its existing 61,440-byte gzip budget.

### Visual review

Run the built homepage in a real browser beside `https://omarchy.org/` at 1440 by 900 and 390 by 844. Confirm the same laser-etch visual grammar, one-shot completion, final-frame palette, and fallback geometry. Exact pixel identity is not required because the effect seed and this repo's hero background differ; the runtime, effect, timing contract, and terminal geometry must match.

## Acceptance Criteria

- The current looping blue/purple color sweep and all of its lifecycle code are removed.
- The homepage uses the pinned local `laseretch` WebAssembly effect and WTE playback runtime.
- The effect plays once per document load and holds its final frame indefinitely.
- The Canvas overlays the existing 81-by-10 ASCII fallback without layout shift at all three contracted viewport sizes.
- Reduced-motion, no-JavaScript, print, unsupported-browser, and failed-load paths show the static Green wordmark.
- A JavaScript or WASM startup failure cannot leave the hero blank for more than two seconds.
- The generated Canvas is ignored by assistive technology and the wordmark exposes one `Omarchy` name.
- All WTE requests are local, all vendored files are pinned and cleared, and the initial JavaScript budget still passes.
- `scripts/build` and the extended rendered-site Chromium checks pass.
- Browser review confirms the local effect matches the production omarchy.org animation behavior.

## Out of Scope

- Replaying the animation on hover, focus, scroll re-entry, navigation dismissal, or a timer.
- Adding user controls for replay, speed, palette, or effect selection.
- Applying Web Text Effects to headers, footer marks, article pages, or other text.
- Reworking the homepage hero composition or scroll-driven panels.
- Reimplementing `laseretch` in CSS or application JavaScript.
- Updating to a newer WTE build than the pinned reference version.
